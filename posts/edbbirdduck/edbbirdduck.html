A brief guide to examining eBird data with duckdb.

I’ve been learning about birdwatching lately and wanted to play around with some observational data. The Cornell Lab of Ornithology provides access to their data on eBird through a data request form. At time of writing, it has over two billion observations. So I thought I’d get two birds stoned at once and learn a bit about setting up duckb databases. It started off with a bit of a journey debugging hardware problems as well.

Overall steps

  1. Make sure your computer isn’t broken.
  2. Download the data.
  3. Extract the relevant .txt.gz to a file or stdin.
  4. Read it into a table in a duckdb database file.
  5. Connect with duckplyr.
  6. Play Analyze

Make sure your computer isn’t broken

Working with the 200GB file revealed some issues on my PC that were generally too rare to notice otherwise. I first noticed this when computing a sha256sum on the giant .tar I downloaded would sometimes give variable results… Uh oh. This lead me on a long journey of fixing some difficult-to-detect problems. Here’s what I suggest you do to avoid this same fate:

  • Run memtest86+
    • Turns out I had a single address in my 64GB memory pool that was faulty, which was the main cause of the errors for me.
    • If there’s a small number of errors near the end of your memory pool, one band-aid solution is to simply restrict the mappable memory to the non-faulty range. Use the the mem kernel parameter as GRUB_BADRAM doesn’t work on 64-bit systems apparently. e.g. add a memory limit on this line in /etc/default/grub GRUB_CMDLINE_LINUX_DEFAULT="splash mem=59GB", then run sudo update-grub.
      • If you fuck up your boot system while doing that 😔, use a live disk to fix it. System76 has a pretty good guide here.
    • Corsair honored their lifetime warranty when I asked for an RMA (5 years after purchase and during an intense RAM crunch where the price is ~2.5x higher than what I initially paid), so kudos to them. I did have to interact with an LLM chatbot to do it though, so anti-kudos.
  • Download the data to a ZFS pool with error correction.
    • I think I was getting some random bit flips here and there (“bit rot”) as the hard drive I was using at first was 15 years old.
    • ZFS is a file system that let’s you maintain big files in a way that is error-correctable. It automatically tracks hashes of chunks of files so you can detect if a chunk has become corrupted. There are some nice guides by FreeBSD and Ubuntu.
    • I got a new hard drive and set it up as a single disk ZFS pool with copies=2. ZFS can theoretically be used to manage bit rot on old drives but I thought it best to just get some new trustworthy hardware.
    • So now I can periodically call zfs scrub to compare each copy of a chunk against the stored hash and fix it if need be. As long as there aren’t any pairs where both chunks are corrupted, the file can be repaired.

Together these techniques should allow me to maintain bit-for-bit data integrity indefinitely and throughout the data processing pipeline. They may be unnecessary if you’re running on institutional computing resources with ECC memory and professionally managed disks. But me, I’m a cowboy 🤠

Creating a database

So, eBird gives us a huge .tar file containing some metadata files and a giant .txt.gz that we want to read into a table in a .duckdb file.

Install duckdb

The duckdb R package includes a ton of code to compile, which means it takes forever to install from source on Linux. The Ncpus argument of install.packages() only installs packages in parallel, but you can make the compilation of a single package’s compiled code run in parallel by setting the j makeflag via the MAKEFLAGS environment variable:

Sys.setenv(MAKEFLAGS = "-j8")
install.packages("duckdb")

This is also useful for other R packages that have tons of compiled code and few dependencies e.g. data.table and rstan.

r2u is also a good option.

Read the file into a database

There are two options on how to do this:

  1. Extract the .txt.gz from the .tar to a file, then let duckdb read that file
  2. Extract the .txt.gz from the .tar to stdin, then let duckdb read stdin

The first option will read the file faster since duckdb’s CSV parser runs in parallel even on gzipped input. However it requires an upfront step of extracting the file, and it requires additional disk space to store that separate copy. Decompressing the .txt.gz to a plain .txt might speed it up as well, but that uses even more space plus it might make things memory bound anyway.

The second option requires less disk space but reading stdin will be single-threaded so if you have a lot of cores it will be slower.

Extract to file

Extract the giant .tar file:

tar xavf ebd_relFeb-2026.tar

When run on a copy on my fast SSD, this command took about 8 minutes.

Then use duckdb to create the database file. Collapsible block as the SQL command is a bit long:

Then run that SQL script using dbExecute() or from the command line:

duckdb -f import.txt ebd.duckdb
  • The resultant .duckdb database file will be slightly larger than the .txt.gz itself since it contains indices and such, but will be much smaller than the input once the latter is decompressed to .txt.
  • You can replace the * with a subset of columns of interest (e.g. to drop the comments columns. Make sure to double quote the column names with spaces). This will use less memory and the database will be smaller, though it will take the same amount of time to read.
  • I notably had to change the estimated types of BCR CODE and PROJECT IDENTIFIERS to VARCHAR because while they appear to be integers in most rows there are a tiny minority formatted as e.g. 1001|1002 or something.
  • duckdb consumes about 2x as much as much memory as the declared limit (long story), so set the limit to ~45% of what you have on your system.
  • Cores improved speed for me up to about 8.
  • On my system this took 35 minutes (about 10 of which were after the progress bar filled completely).
  • I kept the original column names, spaces and all, which necessitates some back ticks when referring to them in R, but you could rename them.
  • I ran this using the duckdb CLI, but if you wanted to do everything from RStudio you could put that whole command in a string in R then run it on a connection to the database file using dbExecute(con, cmd_string)

I ultimately went with the other approach since I had enough space. Using the stdin approach, it took ~75s on my fast SSD to do 10M rows, so extrapolating from that it would take a bit over 3 hours for the whole thing.

Sampling data to another table

There’s another fairly large table one can get which contains the “sampling level” information i.e. the metadata on individual checklists. This is useful e.g. for deduplicating repeated reports from group events. If many birders go on a walk together, it doesn’t make sense to include all their repeated reports of the same bird.

So we need to get this data into another table in the database. The process is similar. Extract the sampling data from it’s tar file:

tar xf ebd_smapling_relMar-2026.tar -C sampling/

For the sake of demonstrating how to do it from R instead of the command line, we’ll do this one with dbExecute. We’ll also let duckdb’s read_csv() function figure out the column types (which works out fine for this table). We’ll put the sampling data into a table called smp:

library(duckdb)

con = dbConnect(duckdb("ebd.duckdb"))

cmd_string = "
SET memory_limit='30GB';
SET threads=12;

CREATE TABLE smp AS
    SELECT * FROM read_csv('sampling/ebd_sampling_relMar-2026.txt.gz',
                           store_rejects = true);
"

dbExecute(con, cmd_string)

Thankfully there are no rare weird entries to trip up the column type detection.

Now we have that table too:

Deduplicate

When individuals submit their own checklists from group outings, it’s common for multiple people to report the presence of the same individual bird. For this reason, we need to deduplicate the checklist data. The auk package uses the following method: within each GROUP IDENTIFIER, retain the entry for each bird from the checklist with the smallest SAMPLING EVENT IDENTIFIER. So you also need to group by SCIENTIFIC NAME because not everyone will report the same set of birds.

There are probably a variety of ways to solve this, but I decided to create another table ddp that keeps track of the sampling event identifiers meeting either of these conditions. That way you can inner_join() that table onto any result to dedup it automatically. I’ll demonstrate this in the next section. For small queries it might be faster to dedupe as needed each time rather than join on this large pre-computed result.

After some experimentation with dbplyr::slice_min + manual tweaks, this is the SQL command I settled on to create ddp:

NoteCreate deduplication table 
ddp_cmd = '
CREATE OR REPLACE TABLE ddp AS
    SELECT "SAMPLING EVENT IDENTIFIER", "SCIENTIFIC NAME" 
    FROM (
      SELECT
        "SAMPLING EVENT IDENTIFIER",
        "SCIENTIFIC NAME",
        "GROUP IDENTIFIER",
        RANK() OVER (PARTITION BY "GROUP IDENTIFIER", "SCIENTIFIC NAME" ORDER BY "SAMPLING EVENT IDENTIFIER") AS col01
      FROM ebd
    ) q01
    WHERE ((col01 <= 1) OR ("GROUP IDENTIFIER" IS NULL))
'

system.time({dbExecute(con, ddp_cmd)})

Should take a few minutes and increase the size of ebd.duckdb by ~5GB.

I’m not 100% confident that it behaves identically to auk::auk_unique() (does one or the other use natural sort and/or account for leading zeros differently?). So if you care about tracking the specific individual people that reported birds then make sure to check that. In my case I just want to drop duplicates, so this will have the same effect even if it doesn’t select the exact same checklist IDs.

Keep in mind that there will still be some computational cost for computing the join. If you want ultimate deduplicated performance could compute the join once and either 1) overwrite the ebd table or 2) store the result in a new table. Option 1 deletes data while option 2 will be highly redundant and nearly double the required disk space.

Another detail I realized during this comparison: Turns out auk_unique() actually pastes together all the sampling event identifiers by group, it doesn’t just take the lowest one like the documentation suggests at first. This behavior could be reimplemented with duckdb I think, but it would be a bit harder than the join method I used above.

But there are some lingering questions:

  • Does the fact that it’s a copies=2 ZFS pool make a difference? I don’t know.
  • Would the difference be larger/smaller on a faster/slower CPU/disk? Don’t know.
  • Is further benchmarking warranted? Couldn’t hurt.

bucket_x = function(x, n = 50) {
  # findInterval is faster/better than cut()
  rng = frange(x)
  
  cuts = seq(rng[1], rng[2], length.out = n)
  
  cents = cuts + (cuts[2] - cuts[1]) / 2
  
  data.table(y = findInterval(x, cuts, rightmost.closed = TRUE)) |> 
    mtt(cent = cents[y]) |> 
    get_elem("cent")
}

llc = ll |>

get_cuts = \(x, n) {

Prior art

I deliberately wrote this post without checking for preexisting work in this area mainly because I wanted to go through this as a learning exercise. But unsurprisingly I’m not the first person to put the eBird data into a database. Mark Isken writes on similar issues in this blog post. He touches on many of the same points. He doesn’t go direct from the input file directly to the database (he writes the tables from an intermediate processing step in R) but he also walks through some topics like zero-filling I didn’t discuss at all.

On the zero-filling point, I think it would be easier to get duckdb to perform that logic than he suggests. Something like this would work I think:

  1. Create a temporary table obs of observed counts
  2. Create a temporary table zeros of all relevant species with count set to 0
  3. z2k = anti_join(zeros, obs)
  • That is, drop all the rows from zeros where there are corresponding entries in the observations
  1. union(obs, z2k)
