mc.cores = 4

I think most people have at least 4 CPU cores these days. Use them.

Why 4?

  • It’s a power of 2.
  • I’d bet that the average R user has at least four cores, I wouldn’t bet that they have eight or more.
  • It’s still in the range where you’re getting big gains from each additional core, but not you’re not dying from the overhead of managing all the resultant pieces.
  • If a package tries to detect a user-set option for parallelization, this is usually it.
  • Stan defaults to four chains, and brms uses this option for its cores argument.

Compare:

set.seed(123)
d = rexp(8e7)
t1 = system.time({parallel::mclapply(d, sqrt)})
t1
   user  system elapsed 
   33.9     7.7    26.9

Versus:

options(mc.cores = 4)
set.seed(123)
d = rexp(8e7)
t2 = system.time({parallel::mclapply(d, sqrt)})
t2
   user  system elapsed 
     20      14      14

brms.backend = cmdstanr

From what I can tell, cmdstanr improves upon rstan in practically every way. It’s faster, updates more frequently, and IMO is easier to use. It just isn’t available on CRAN, which is unfortunate (supposedly the instantiate package allows CmdStan based packages to precompile models in a way that is CRAN friendly).

This option tells brms to always use cmdstanr so you don’t have to set the backend argument every time. Example:

rstan_time = system.time({
  rstan_mod <- brm(r2 ~ (Anger + Gender + btype + situ)^2 + (1 | id) + (1 | item), 
                   family = bernoulli, 
                   data = VerbAgg,
                   file = "fits/rstan_sleep")
})

Versus:

options(brms.backend = "cmdstanr")
cmdstanr_time = system.time({
  cmdstanr_mod <- brm(r2 ~ (Anger + Gender + btype + situ)^2 + (1 | id) + (1 | item),
                      family = bernoulli, 
                      data = VerbAgg,
                      file = "fits/cmdstanr_sleep")
})

Look at how much faster both the compilation and sampling is:
